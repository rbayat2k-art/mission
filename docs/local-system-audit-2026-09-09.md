## قرارداد هویت درخواست و حفظ صف

- `X-Tapra-User-Id` صرفاً هویت مورد انتظار است، نه راه احراز هویت. Cookie معتبر و کنترل نقش همچنان الزامی است.
- عدم تطابق، پاسخ خصوصی `409` با `ACCOUNT_CONTEXT_CHANGED` می‌دهد و هیچ عملیات دامنه‌ای اجرا نمی‌شود.
- کلاینت این حالت را تعارض نسخه تسک فرض نمی‌کند؛ صف حساب مبدأ دست‌نخورده می‌ماند تا ورود همان حساب.
- نبود هدر برای سازگاری با نسخه‌های قدیمی پذیرفته می‌شود؛ تضمین جدید مختص درخواست‌های به‌روزشده است، نه همه APKها و تب‌های قدیمی.
- ۴۰۱، ۴۰۸، ۴۲۵، ۴۲۹ و ۵xx صف را برای تلاش بعدی حفظ می‌کنند. سایر ردها برای تصمیم صریح نگهداری می‌شوند؛ تازه‌سازی آنها را بی‌نهایت دوباره نمی‌فرستد.
- اعمال مجدد نتیجه تسک فقط برای `409 + TASK_VERSION_CONFLICT` مجاز می‌ماند. رد اعتبارسنجی یا عملیات حساس خودکار بازنویسی نمی‌شود.
- خطای GPS batch همچنان بدون ACK نهایی حذف نمی‌شود. payload و جزئیات خصوصی پاسخ در پیام تشخیصی تازه قرار نمی‌گیرند.
- تغییر نسخه IndexedDB یا انتقال/پاک‌سازی رکوردهای قدیمی لازم نشده است.

## آزمون و محدودیت شواهد

- تست‌های واحد نهایی: ۱۲۹ موفق، صفر شکست و صفر skip در اجرای دارای JDK.
- تست Java، خود کلاس `TrackingRequestScope` را compile و اجرا می‌کند؛ کامپایل کل Android یا شبیه‌سازی سرویس سیستم‌عامل نیست.
- تست auth کد واقعی را با وابستگی دیتابیس ساختگی اجرا می‌کند؛ تست SQL و session واقعی چندکاربره محسوب نمی‌شود.
- تست مرورگر از Chrome واقعی و نمای Pixel 5 استفاده می‌کند. این، Android WebView واقعی یا Chrome قدیمی نصب‌شده روی دستگاه نیست.
- TypeScript، Lint، Build سایت و `git diff --check`: موفق روی تغییرات نهایی.
- E2E کامل روی build نهایی: **۲۷ موفق، صفر شکست، یک skip عمدی** (آزمون مخصوص موبایل در پروژه دسکتاپ). از این مجموعه، ۱۸ تست مربوط به انتقال آفلاین جدید در دسکتاپ و نمای Android هستند.
- درخواست HTTP واقعی به سرور تست: JSON نامعتبر ورود پاسخ ۴۰۰ و Cookie نامعتبر پاسخ ۴۰۱ داد؛ بدون دسترسی به DB.
- ممیزی آنلاین npm: در دو تلاش اتصال به `registry.npmjs.org/-/npm/v1/security/advisories/bulk` با `ECONNRESET` قطع شد؛ این آزمون **موفق نیست** و پاک‌بودن وابستگی‌ها اثبات نشده است.
- برای build و سرور آزمون، اتصال DB به loopback/پورت غیرعملیاتی و `AUTO_MIGRATE=false` تنظیم شد؛ هیچ دیتابیس واقعی برای تست استفاده نشد. فایل `.env` و `.env.local` ویرایش یا در خروجی نمایش داده نشدند.

## موارد باقی‌مانده، نه اصلاح‌شده

1. **تست انتشار اندروید:** Android SDK، Gradle و adb در محیط در دسترس نیست؛ نصب/ارتقا، مجوز دقیق، خاموشی نمایشگر، process kill، Doze و تعویض حساب روی API 23/29/35 باید در محیط آماده تکرار شوند. Force Stop را نمی‌توان مانند سرویس همیشه‌فعال تضمین کرد.
2. **Exactly-once در کل سامانه:** lock صف از ارسال هم‌زمان جلوگیری می‌کند، اما پاسخ گم‌شده پس از ذخیره سرور هنوز برای مسیرهای فاقد شناسه idempotency، مانند ضمیمه و بعضی integrity eventها، نیازمند قرارداد و تست جداست. در مرورگر فاقد Web Locks هم تضمین بین چند تب وجود ندارد؛ تک‌صفحه همچنان محافظت می‌شود.
3. **ظرفیت/خرابی صف بومی:** سقف فعلی ۳۰۰۰ نقطه و رفتار JSON خراب در SharedPreferences باید با سیاست بازیابی و ظرفیت دیسک بررسی شود. این دور سقف، داده تاریخی یا قواعد کارکرد را تغییر نداده است.
4. **state اتصال وب:** timestamp قطع اینترنت در `app/page.tsx` هنوز کلید مشترک دارد؛ اتصال آن به حساب و work session و تطبیق با مرزهای فعالیت باید قبل از اتکای مدیریتی به این رویدادها آزمون شود. داده ساختاریافته heartbeat و گزارش باید مرجع بماند.
5. **اعتبارسنجی ورودی سایر APIها:** بررسی نوع ورودی در همه routeها یکدست نیست؛ در این دور فقط خطای اثبات‌شده ورود اصلاح شد. fuzzing مأموریت/مرحله/فایل هنوز کامل نیست.
6. **امنیت ارسال Push:** پذیرش endpoint صرفاً HTTPS برای دفاع کامل SSRF کافی نیست. سیاست مقصد مجاز و کنترل خروجی شبکه با لحاظ Providerهای واقعاً مورد استفاده باید مشخص و آزمایش شود. پاک‌سازی log جای این کنترل را نمی‌گیرد.
7. **بازبینی ساختاری بعدی:** استخراج تدریجی state حساب، گزارش و صف از صفحه بزرگ، بدون بازطراحی ظاهر یا تغییر محاسبات؛ افزودن تست واقعی چهار/پنج حساب روی DB آزمایشی؛ تست تاریخ مرزی، خروجی Excel و هم‌زمانی مأموریت‌ها.
8. **AI آزمایشی:** branch جداگانه AI بخشی از همین patch نیست و پیش از هر انتشار جداگانه باید مجدداً بررسی شود.

## پیگیری کاربردی: عکس مأموریت و سرعت مسیر — ۲۰۲۶-۰۹-۰۹

کاربر مشخص کرد مشکل عکس داخل **اپ نصب‌شده اندروید** رخ می‌دهد. در این دور نیز فقط شاخه محلی `codex/system-audit-2026-09-09` تغییر کرد؛ اصلاحات قبلی و worktree مستقل AI حفظ شد. main، GitHub، سرور و داده واقعی تغییر نکرد. از مهارت/ایجنت تیم توسعه تاپرا استفاده نشد. این بخش طبق راهنمای عمومی مستندسازی، دلیل تصمیم‌ها و محدودیت شواهد را ثبت می‌کند.

### ایرادهای اثبات‌شده و اصلاح محلی

1. **صفحه تصویر به‌اشتباه سفید تشخیص داده می‌شد.** لینک فایل، صفحه جداگانه باز می‌کرد؛ تابع `verifyRenderedPage` در اندروید فقط وجود متن بیش از ۸ کاراکتر را نشانه سلامت می‌دانست. سندی که فقط تصویر داشت از این شرط رد می‌شد و وارد مسیر بازیابی می‌شد. اکنون شرط بومی، تصویر واقعاً decode‌شده را نیز می‌پذیرد. این عبارت جاوااسکریپت با سند تصویری سالم، خراب و HTML خالی آزمون شد. بدون لاگ گوشی نمی‌توان اثبات کرد تنها علت رخداد همان کارمند همین بوده است.
2. **نمایش امن عکس داخل همان مأموریت.** `AttachmentLink` به‌جای رفتن به صفحه/مرورگر دیگر، تصویر را با نشست جاری و هدر حساب دریافت می‌کند و داخل یک پنجره قابل‌بستن نمایش می‌دهد. اندازه اصلی، نمایش متناسب، خطای خواندن تصویر، timeout پانزده‌ثانیه‌ای، تلاش دوباره دستی و کنترل فوکوس/کلید Escape دارد. Blob فقط در حافظه است؛ هنگام خروج URL آن آزاد و درخواست لغو می‌شود. هیچ Cookie به برنامه خارجی منتقل نمی‌شود و دسترسی فایل عمومی نشده است. فایل‌های عکس گفت‌وگوی پیگیری نیز از همین نمایشگر استفاده می‌کنند.
3. **پاسخ دیررس فایل مأموریت قبلی.** بارگیری فهرست فایل در `MissionBriefAttachments` بر اساس حساب و مأموریت جدا شد؛ جابه‌جایی، درخواست قبلی را لغو می‌کند و فهرست/تصویر قبلی را نگه نمی‌دارد. خطای دریافت فهرست دیگر به شکل «فایلی وجود ندارد» پنهان نمی‌شود. پاسخ موفق فهرست سمت سرور `private, no-store` است.
4. **میانگین سرعت با زمان گرد‌شده.** اجرای الگوریتم HEAD روی داده مصنوعی، میانگین **۴۰** را برای نمونه نزدیک به **۶۰ km/h** نشان داد. نسخه اصلاحی از میلی‌ثانیه و مسافت گردنشده همان بازه‌ها استفاده می‌کند و **۶۰** برمی‌گرداند. در مأموریت چندمرحله‌ای هم ابتدا مقادیر دقیق جمع و سپس فقط نمایش گرد می‌شود.
5. **بیشترین سرعت نامعتبر.** الگوریتم قبلی سرعت خام خراب گوشی را وارد بیشینه می‌کرد؛ همان آزمایش با داده مصنوعی، **۳۲۴۰۰ km/h** تولید کرد. مسیر چندمرحله‌ای هم جهش ردشده را وارد بیشینه می‌کرد. اکنون سرعت گزارش از فاصله/زمان بازه‌های پذیرفته‌شده به‌دست می‌آید و سقف موجود ۱۶۰ رعایت می‌شود. سرعت منفی، نامتناهی، غیرعددی و خارج از سقف هنگام دریافت نقطه به null تبدیل می‌شود؛ خود نقطه GPS معتبر صرفاً به‌خاطر سرعت جانبی خراب حذف نمی‌شود. مقادیر قدیمی نامعتبر نیز در پاسخ آخرین موقعیت، سرعت معتبر معرفی نمی‌شوند.
6. **بازه بی‌GPS به‌اشتباه توقف قطعی بود.** تفاضل کل زمان سفر و حرکت، زمان فاقد داده را نیز توقف می‌نامید. توقف گزارش مأموریت اکنون فقط از بازه‌های دارای نقاط پذیرفته‌شده محاسبه می‌شود. تغییر نشست، جهش نامعتبر و فاصله نمونه‌های بیش از دو دقیقه وارد حرکت/توقف یا بیشینه سرعت نمی‌شوند و پوشش ناقص می‌شود.
7. **خرابی یک ورودی جانبی GPS می‌توانست کل درخواست را خراب کند.** نوع شناسه‌ها قبل از trim بررسی می‌شود؛ بدنه null و اعضای نامعتبر آرایه باعث خطای کنترل‌نشده نمی‌شوند. heading و altitude غیرعددی/نامتناهی نیز null می‌شوند، بدون حذف نقطه جغرافیایی معتبر.

### معنی اعداد و حدود این اصلاح

- این داده‌ها **تخمین GPS** هستند، نه اندازه‌گیری تضمین‌شده سرعت لحظه‌ای یا شواهد تقلب. سرعت گزارش، میانگین فاصله/زمان بین نمونه‌های پذیرفته‌شده است؛ سرعت نمایش «آخرین موقعیت» همچنان اندازه‌گیری گوشی در زمان همان نقطه است، نه سرعت زنده کنونی در صورت کهنه‌بودن نقطه.
- سقف جهش ۱۶۰ km/h و حد حرکت ۵ km/h حفظ شده‌اند. حرکت بسیار آهسته و خطای GPS همچنان محدودیت اندازه‌گیری‌اند. اعتبار اولیه نقاط گزارش همچنان همان دقت حداکثر ۱۰۰ متر است؛ خطای کم‌تر از سقف سرعت الزاماً قابل‌تشخیص نیست.
- پنجره قابل‌اتکای محاسبه حرکت مأموریت از ۲۰ دقیقه به **۲ دقیقه**، هم‌راستا با قطع خط مسیر تاریخی، کاهش یافته است. اتصال فرضی دو نقطه با وقفه طولانی سرعت واقعی را ثابت نمی‌کند. این تصمیم فقط در گزارش مسیر مأموریت اعمال شده؛ محاسبه قدیمی «کل مسافت نقاط روزانه» تابع جداگانه است و در این دور تغییر نکرده است.
- در مأموریت چندمرحله‌ای، صورت و مخرج میانگین از همان بازه‌های حرکت‌اند؛ مسافت توقف/نوسان آهسته دیگر به صورت کسر میانگین سرعت اضافه نمی‌شود. زمان‌های بین مراحل بسته و شروع مرحله بعد به هم متصل نمی‌شوند.
- جمع «حرکت + توقف ثبت‌شده» در پوشش ناقص ممکن است از کل زمان سفر کمتر باشد. متن گزارش این تفاوت و تخمینی‌بودن سرعت را توضیح می‌دهد. عنوان ستون‌های سرعت Excel نیز واحد km/h و ماهیت تخمینی دارد.
- **هیچ migration، بازنویسی GPS، تغییر مأموریت، امتیاز یا فرمول حضور انجام نشده است.** پس از انتشار احتمالی، اعداد مشتق‌شده گزارش‌های قدیمی هم با الگوریتم اصلاحی خوانده می‌شوند؛ پیش از انتشار باید این تفاوت روی نمونه مورد توافق بررسی شود. فایل Excel قبلاً دانلودشده تغییر نمی‌کند.

## آزمون عملی مدیر، سرپرست و کارمند — ۲۰۲۶-۰۹-۰۹

### قرارداد افزوده پیام و سازگاری

- `POST /api/follow-up-requests/:id/messages` هنوز `text` می‌گیرد؛ کلاینت جدید `clientMessageId` از نوع UUID v4 هم می‌فرستد. کلاینت قدیمی بدون این فیلد پذیرفته می‌شود اما تضمین retry جدید را ندارد.
- رکورد جدید ۲۰۱، تکرار همان شناسه/نویسنده/درخواست/متن ۲۰۰ با `duplicate:true`، استفاده ناسازگار از شناسه ۴۰۹، عدم مجوز ۴۰۳ و ورودی نامعتبر ۴۰۰ است.
- تکرار موفق، سابقه و اعلان دیگری تولید نمی‌کند. همان پیام ثبت‌شده حتی پس از بسته‌شدن گفت‌وگو قابل دریافت مجدد است؛ پیام جدید در گفت‌وگوی بسته/مأموریت لغوشده رد می‌شود.
- از کلید اصلی موجود پیام استفاده شده؛ تغییر schema لازم نیست. mutex تست در حافظه، اثبات قفل‌های MySQL نیست.
- UUID کلاینت از `crypto.getRandomValues` ساخته می‌شود؛ به `crypto.randomUUID` که در بعضی مرورگرهای قدیمی نیست وابسته نیست.
- پل بومی جدید افزایشی است و پل قبلی برای APKهای قبلی باقی می‌ماند. بررسی هویت اتمی جدید فقط پس از نصب APK دارای این متد اعمال می‌شود؛ کنترل پاسخ دیررس وب برای هر دو مسیر وجود دارد.

### سناریوهای اجراشده و سطح شواهد

1. **رابط مدیر و کارمند:** پیام مدیر + دو فایل مصنوعی؛ فایل دوم بار اول ۵۰۳، retry فقط همان فایل؛ یک پیام و دو ضمیمه نهایی؛ کارمند پیام را می‌بیند و پاسخ می‌دهد؛ مدیر پاسخ را می‌بیند و تصمیم بازگشت به پیگیری می‌فرستد.
2. **رابط سرپرست:** جزئیات درخواست A معطل می‌ماند؛ B انتخاب می‌شود؛ پاسخ دیررس A نادیده می‌ماند و ارسال به B می‌رود.
3. **مأموریت خودساخته:** عنوان، شرح، اولویت و تاریخ/ساعت؛ دو submit در یک نوبت؛ فقط یک POST؛ شکست تازه‌سازی لیست، پیام «ثبت شد؛ دوباره نسازید» می‌دهد.
4. **مأموریت دو تسک:** فعالیت از fixture فعال است؛ GPS مصنوعی مرورگر، شروع مأموریت، ثبت مقصد، تعیین وضعیت هر دو تسک، ممنوع‌بودن ادامه قبل از تعیین همه و ثبت نهایی؛ لمس سریع هر عملیات فقط یک درخواست می‌فرستد. این سناریو شروع/پایان خودِ شیفت روزانه را اجرا نمی‌کند.
5. **اعلان:** GET ناموفق با صندوق خالی اشتباه نمی‌شود؛ PATCH ناموفق، اعلان را خوانده‌شده جلوه نمی‌دهد؛ retry موفق؛ پل Android هویت حساب را می‌گیرد؛ logout هنگام معطل‌بودن decode، اعلان حساب قبلی را نمایش نمی‌دهد.
6. **منطق واقعی API با وابستگی ساختگی:** مدیر، سرپرست A/B و کارمند A/B؛ اتصال فایل به ID پیام و دریافت همان بایت‌ها توسط فرد مجاز؛ رد فرد غیرمجاز؛ ۲۰ درخواست هم‌زمان یک پیام با یک ID، یک پیام/سابقه/اعلان؛ تعارض شناسه، وضعیت بسته و گیرنده escalation.
7. **API اعلان با داده مصنوعی:** ۶۱ اعلان نخوانده و لیست ۵۰تایی؛ شمارنده ۶۱؛ خواندن یکی و همه فقط در حساب مربوط؛ `markAll` نامعتبر و حساب ناسازگار بدون write.
8. **مجموعه‌های قبلی:** عکس درون‌صفحه و خرابی/timeout آن، صف آفلاین و تعویض حساب/چند تب، فاصله و سرعت، GPS gap و lifecycle بومی دوباره اجرا شدند.

تست رابط روی Chrome واقعی دسکتاپ و Chrome با نمای Pixel 5 و HTTP fixtures اجرا شد. نقش‌ها در درخواست‌های ساختگی مستقل‌اند؛ session واقعی MySQL/رمز/کوکی چندنفره در این E2E ایجاد نشده است. تست API، خود فایل route را با DB/storage/auth جایگزین در حافظه اجرا می‌کند؛ SQL واقعی، lock دیتابیس و تحویل Push سیستم‌عامل را تضمین نمی‌کند. آزمون قدیمی Chrome صرفاً fallback نبود Web Locks و سازگاری کد است، نه نصب Chrome 80.

### ریسک‌های باقی‌مانده و شرط انتشار

- نتیجه این دور «همه باگ‌ها پیدا و رفع شدند» نیست؛ انتشار هنوز متوقف است. main و HEAD روی مبنای قبلی‌اند و این اصلاحات Commit نشده‌اند.
- آماده‌سازی محیط Android و تست نصب واقعی/خاموشی صفحه/باتری/GPS در پس‌زمینه، ارتقای APK و حساب‌های مختلف ضروری است. پل ساختگی و Java خالص جای APK واقعی نیست.
- قفل هم‌زمان UI جای idempotency سرور را نمی‌گیرد. گم‌شدن پاسخ پس از ذخیره فایل یا مأموریت و سپس reload هنوز می‌تواند برای endpoint فاقد ID تکرار ایجاد کند؛ بازسازی draft فایل پس از بستن برنامه پیاده نشده است. پنل گفت‌وگو فقط retry همان صفحه را نگه می‌دارد.
- notification پس از commit پیام تولید می‌شود؛ شکست ذخیره اعلان پس از commit پیام یا مرگ process در این فاصله هنوز outbox سروری مستقل ندارد. replay پیام موجود اعلان دوباره ایجاد نمی‌کند؛ تحویل نهایی اعلان در این حالت تضمین نشده است.
- سناریوی برخورد عمدی یک UUID هم‌زمان در دو درخواست متفاوت و unique-key دیتابیس باید روی MySQL واقعی آزمون شود؛ ممکن است خطای DB نیازمند تبدیل به conflict باشد.
- همه تصمیم‌های سرپرست، مسابقه لغو/تکمیل واقعی، مدارک غیرتصویری با برنامه خارجی، export واقعی Excel، محاسبات شیفت روی DB و upload بسیار بزرگ به تست مستقل بیشتر نیاز دارند. معیارهای قبلی انتشار و امنیت در بخش‌های بالا همچنان معتبرند.
- ظاهر فعلی حفظ شده؛ این دور بازطراحی UI یا افزودن تصمیم خودکار مدیریتی نیست.

### قرارداد افزایشی API و مرز سازگاری

- `GET /api/missions`: فیلد اختیاری `destinationRegisteredAt: string | null` از آخرین `mission_destinations.created_at` همان مأموریت. زمان سرور است و قانون ثبت مقصد تغییر نکرده؛ schema جدیدی ساخته نشده است.
- `POST /api/destinations`: فیلد اختیاری `destination.registeredAt` زمان سرور را به پاسخ موفق هر دو مسیر تک‌مرحله‌ای و چندمرحله‌ای اضافه می‌کند.
- کلاینت قدیمی این فیلدهای افزایشی را نادیده می‌گیرد. کلاینت جدید در نبود فیلد، پس از پاسخ موفق/صف‌شدن، زمان محلی را تنها برای نمایش جاری استفاده می‌کند؛ با بارگذاری بعدی، اطلاعات سرور مرجع است. اثبات رسیدن آفلاین پس از reload همچنان به همگام‌شدن صف وابسته است.
- `missionWorkEntryStep` صرفاً تصمیم نمایشی است، هیچ درخواست، محاسبه امتیاز یا نوشتن دیتابیس ندارد. برای چندمرحله‌ای، `arrivedAt` قدیمی در مرحله بازگشایی‌شده با وضعیت `in_progress` معتبر محسوب نمی‌شود؛ مرحله باید `arrived` باشد.
- کنترل‌های اصلی ضد Double Click دور قبل حفظ شده‌اند. این محافظ UI به معنای تضمین exactly-once برای تمام endpointها پس از قطع پاسخ و reload نیست.

### آزمون واقعی دیتابیس، مستقل از داده کاربر

MariaDB نصب‌شده در `C:\Program Files\MariaDB 12.3\bin` پیدا شد؛ نسخه اجرایی **۱۲.۳.۳** است، نه نسخه‌های MySQL 8.4/MariaDB 10.11 در CI. instance تازه فقط روی `127.0.0.1:33379` با data directory مستقل `work/audit-db-20260909/data` اجرا شد؛ Windows Service ساخته نشد. هیچ تنظیم دیتابیس اصلی یا فایل env ویرایش یا نمایش داده نشد.

1. آزمون موجود `tests/integration/mysql-schema.mjs` روی دو schema تازه اجرا شد: ساخت اولیه، migration دوباره، upgrade داده legacy مصنوعی، حفظ checksum رکوردها، FK/index و backfill دفتر امتیاز بدون تکرار. هر دو موفق؛ همان دو schema موقت طبق cleanup خود آزمون حذف شدند و قابل بازسازی‌اند.
2. `tests/integration/local-api-workflow.mjs` با محافظ مسیر datadir/پورت/نام schema/URL، یک schema دیگر و **پنج حساب ساختگی** (مدیر، سرپرست A/B، کارمند A/B) ایجاد می‌کند؛ setup در صورت وجود schema متوقف می‌شود و هیچ schema موجودی را جایگزین نمی‌کند.
3. آزمون دوم API واقعی Build مستقل را روی `127.0.0.1:3239` فراخواند؛ Cookie فقط در حافظه آزمون نگه داشته شد. فایل آپلود در زیرشاخه work آزمایشی ذخیره شد. Reverse geocoding به loopback بدون سرویس هدایت شد؛ اطلاعات GPS واقعی استفاده نشد و مقصد خارجی تماس گرفته نشد.
4. این نه بررسی DB واقعی شرکت، نه تأیید رفتار نسخه DB سرور و نه اثبات تحویل اعلان گوشی است. DB/فایل‌های ساختگی API در پوشه work نگه داشته شده‌اند؛ اطلاعات کاربران واقعی دست‌نخورده‌اند.

نه گروه آزمون HTTP/SQL موفق، علاوه بر ورود واقعی پنج حساب:

- رد شروع مأموریت دیگران، تخصیص سرپرست غیرمجاز و هدر حساب ناسازگار؛
- ۱۰ درخواست شروع هم‌زمان → یک رویداد شروع در MariaDB؛
- وجود زمان رسیدن در GET و رد پایان مأموریت با تسک باز؛
- ۲۰ درخواست یکسان نتیجه تسک → یک event؛ expectedVersion قدیمی → ۴۰۹؛
- ۲۰ ارسال تکراری پیام → یک پیام، یک audit و یک notification ذخیره‌شده؛
- آپلود واقعی فایل مصنوعی مدیر و دریافت عین بایت‌ها توسط سه حساب مجاز؛ رد فایل و گفت‌وگو برای دو حساب غیرمجاز؛
- بازگشت پیگیری توسط مدیر بدون پایان فعالیت روزانه کارمند؛
- گزارش روزانه، هفتگی، ماهانه مدیر/سرپرست/کارمند و پاسخ فایل XLSX واقعی (کنترل امضای ZIP؛ محتوای workbook جدا در Unit آزموده شده)؛
- logout و رد Cookie نشست قبلی.

در اجرای مجدد fixture، تلاش برای شروع شیفت دوم با شناسه متفاوت به‌درستی ۴۰۹ شد. آزمون برای تکرارپذیری، قبل از شروع شیفت وضعیت جاری را می‌خواند و از شیفت همان حساب آزمایشی استفاده می‌کند؛ منطق سرور برای عبور آزمون تضعیف نشد.
