# مرتب‌سازی مسئول مأموریت — بررسی و پیاده‌سازی محلی

## هدف و محدوده

در فرم قبلی، کاربران به ترتیب زمان ساخت حساب می‌آمدند و اولین کاربر فعال خودکار انتخاب می‌شد. درخواست جدید، دسترسی آسان‌تر به افرادی است که مدیر بیشتر به آن‌ها کار می‌دهد و کاهش ارجاع اشتباه. این تغییر از main منتشرشده `5726b57445f1d934bb97fc22b60fd15975a5067b` روی شاخه `codex/recent-mission-assignees` پیاده شده است. تحویل اولیه فقط محلی بود؛ کاربر در ۲۰۲۶/۰۹/۱۲ انتشار مشروط به موفقیت بررسی‌ها را تأیید کرد. نسخه هدف وب **2.10.3** است؛ کد بومی Android و داده‌های مأموریت تغییر نمی‌کنند.

## قاعده انتخاب‌شده

1. تعداد ثبت مأموریت‌های ۳۰ روز اخیر توسط **همین حساب مدیر/مالک/سرپرست** برای هر فرد، نزولی.
2. در تعداد برابر، زمان آخرین ثبت جدیدتر بالاتر.
3. بدون سابقه یا در تساوی کامل، نام فارسی، نام کاربری و سپس شناسه برای ترتیب ثابت.

این قاعده «فقط آخرین نفر» یا تعداد کل عمر سامانه نیست؛ بازه ۳۰ روز برای نمایندگی همکاری‌های فعلی انتخاب شده و در راهنمای فرم شفاف است. هیچ AI، کلید API، ارسال اطلاعات خارجی یا ذخیره ترجیحات مرورگر لازم نیست.

افراد دارای سابقه در گروه «ارجاع‌های پرتکرار اخیر شما» و بقیه در «سایر افراد» دیده می‌شوند. نام، نقش و نام کاربری کنار هم می‌آیند تا افراد هم‌نام قابل تشخیص باشند. فرم جدید از گزینه خالی شروع می‌شود و مسئول باید صریح انتخاب شود. در ویرایش، مسئول فعلیِ فعال و مجاز حفظ می‌شود؛ اگر دیگر مجاز نباشد، هیچ جایگزینی خودکار نیست. هنگام تایپ، ترتیب فهرست جابه‌جا نمی‌شود؛ بازکردن بعدی فرم، سابقه تازه سرور را می‌خواند.

## منبع سابقه و محدودیت عمدی

از رویدادهای موجود و تغییرناپذیر `audit_logs` با عمل `mission.created`، actor حساب جاری و `details.assignedTo` استفاده می‌شود. مأموریت باید هنوز موجود، غیرلغوشده و متعلق به همان گیرنده ثبت اولیه باشد. دلیل: شمارش صرف `missions.created_by` و گیرنده فعلی، ارجاع مجدد مدیر دیگری را اشتباهاً به مدیر اولیه نسبت می‌دهد.

ویرایش عنوان/مدارک، retry بارگذاری و ارجاع مجدد هنگام ویرایش، **ثبت مأموریت جدید محسوب نمی‌شوند** و امتیاز این مرتب‌سازی را زیاد نمی‌کنند. مأموریت‌های حذف‌شده/لغوشده/منتقل‌شده و رویدادهای قدیمی ناقص یا بدون گیرنده معتبر وارد پیشنهاد نمی‌شوند. رویدادهای خراب با JSON_VALID کنار گذاشته می‌شوند؛ داده قدیمی اصلاح یا حذف نمی‌شود. شمارش DISTINCT از دوباره‌شماری مأموریت جلوگیری می‌کند.

## API و امنیت

`GET /api/missions/assignees` مخصوص فرم ثبت/ویرایش است؛ فهرست عمومی مدیریت کاربران و ترتیب آن تغییر نکرده‌اند.

- مجاز: owner، admin و supervisor؛ کارمند/مهمان رد می‌شوند.
- سرپرست فقط کارکنان مستقیم فعال فعلی خودش را می‌بیند؛ همین محدودیت در هر دو query کاربران و سابقه اعمال می‌شود.
- هویت از Session سمت سرور است؛ شناسه حساب در query string هیچ اثری ندارد. هدر `X-Tapra-User-Id` مانع استفاده از حساب عوض‌شده در تب دیگر است.
- خروجی: `accountId`، `historyDays: 30`، `orderMode: recent|name` و `assignees` شامل `id/fullName/username/role/recentAssignmentCount/lastAssignedAt`.
- پاسخ خصوصی و `no-store` است و `Vary: Cookie, X-Tapra-User-Id` دارد. هیچ GPS، متن مأموریت، اطلاعات audit خام، شماره تلفن یا رمز در خروجی نیست.
- تنها SELECT اضافه شده؛ schema، رویدادهای قدیمی و مسیر ثبت/محاسبه امتیاز تغییر نکرده‌اند.
- اگر خواندن سابقه خطا بدهد، لیست مجاز به ترتیب نام برمی‌گردد و رابط صریحاً حالت جایگزین را می‌گوید؛ خطای خام دیتابیس نشان داده نمی‌شود. شکست خواندن خود فهرست، فرم قدیمی را باز نمی‌کند.
- درخواست فرم با خروج از پنل یا تغییر حساب لغو می‌شود؛ پاسخ ناسازگار با حساب رد می‌شود. فهرست فرم از رفرش سایر فهرست‌های مدیر مستقل است. ثبت/ویرایش هم هدر هویت جاری دارد و کنترل مقصد سمت سرور موجود حفظ می‌شود.

## فایل‌های تغییر

- `app/api/missions/assignees/route.ts`: API فقط‌خواندنی و محدود به حساب.
- `lib/mission-assignee-order.ts`: قرارداد و ترتیب قطعی بدون تغییر آرایه ورودی.
- `app/page.tsx`: بارگذاری فهرست مخصوص، انتخاب صریح، گروه‌بندی و راهنمای کوتاه.
- `tests/mission-assignee-order.test.mjs`: تست منطق ترتیب و اجرای route واقعی با DB/auth مصنوعی.
- `tests/e2e/mission-assignee-order.spec.ts`: فرم واقعی با API مصنوعی در دسکتاپ و نمای Android Chrome.
- `tests/integration/mission-assignee-history.mjs` و اتصال آن در `tests/integration/mysql-schema.mjs` / `tests/ci-workflows.test.mjs`: اجرای SQL واقعی route روی schema آزمایشی تازه و ارتقایافته، با پنج نقش/حساب و بازگردانی کامل fixture؛ خطای SQL با fallback نمی‌تواند تست را موفق کند.
- `VERSION`، `lib/app-version.ts` و نسخه ریشه `package.json`/`package-lock.json`: شماره انتشار وب 2.10.3، بدون تغییر وابستگی.

## اعتبارسنجی و محدودیت انتشار

TypeScript، ESLint و ۲۴۳ Unit موفق‌اند. Build و بسته‌بندی با Next محلی **16.3.1** موفق شد. دریافت Next **16.3.4** مطابق lockfile و Audit آنلاین هر دو با `ECONNRESET` از Registry رسمی متوقف شدند؛ تنظیم Registry، Proxy یا DNS تغییر نکرد. هیچ وابستگی یا نسخه‌ای تغییر نکرده است. این Build محلی جای تأیید Build دقیق انتشار نیست.

تست محلی SQL/auth با زیرساخت مصنوعی است؛ در مرحله آماده‌سازی انتشار، اجرای query واقعی روی schemaهای مستقل MariaDB 10.11 و MySQL 8.4 به harness فعلی CI اضافه شد. این اجرا باید قبل از انتشار موفق شود. تست مرورگر از سرور محلی 127.0.0.1 و API/GPS مصنوعی استفاده می‌کند؛ هیچ حساب یا دیتابیس Production به کار نرفته است. کد بومی APK تغییر نکرده و این نوبت آزمایش روی گوشی فیزیکی ادعا نمی‌شود.

در اولین اجرای E2E جدید، ۱۰ تست موفق و ۴ شکست مربوط به selector خود fixture بود: کلاس toast پنل مدیر متفاوت و کلیدهای تعویض پنل دارای نقش tab بودند. selectorها مطابق رابط واقعی اصلاح شدند؛ شرط محصول یا تست امنیت حذف نشد. بازاجرای کل مجموعه ۱۰۱ موفق و یک skip عمدی داشت. بازبینی مستقل سپس یک پیام خطای قدیمی وابسته به فهرست پس‌زمینه را پیدا کرد؛ پیام نیز به فهرست مخصوص فرم متصل شد و دو تست رگرسیون دسکتاپ/موبایل برای آن اضافه شدند.

اجرای نهایی پس از بازسازی برنامه: **۱۰۳ تست مرورگر موفق، صفر ناموفق و یک skip عمدی** (تست مخصوص موبایل در پروژه دسکتاپ). هر ۱۶ سناریوی جدید فرم در دو نمای دسکتاپ و Android Chrome موفق بودند. TypeScript، ESLint، Build محلی و هر ۲۴۳ Unit نیز پس از اصلاح نهایی دوباره موفق شدند. تصویر واقعی فرم آزمایشی موبایل در `test-results/mission-assignee-order-rec-00a1b-equire-deliberate-selection-android-chrome/recent-assignees-form.png` ثبت و از نظر خوانایی بازبینی شد؛ این فایل خروجی تست و خارج از Git است.

## دروازه انتشار تأییدشده

پس از تأیید کاربر، اتصال رسمی GitHub و SSH بررسی شد؛ origin/main و سرور هر دو روی نسخه پایه بالا بودند و سلامت داخلی 2.10.2 موفق بود. تلاش دوباره برای نصب دقیق و Audit روی کامپیوتر همچنان با ECONNRESET شکست خورد؛ به همین دلیل فقط شاخه توسعه برای اجرای CI فرستاده می‌شود. تا موفقیت ساخت دقیق، Lint، TypeScript، Unit، E2E، Audit و تست دیتابیس‌های مستقل MariaDB/MySQL و بررسی Android، main تغییر نمی‌کند.

بعد از موفقیت CI، فقط ادغام fast-forward همان commit بررسی‌شده مجاز است. Deploy فقط با deploy.sh رسمی انجام می‌شود و باید پشتیبان دیتابیس، مهاجرت افزایشی موجود، سلامت داخلی/عمومی و سرویس systemd بررسی شوند. نتیجه واقعی CI/انتشار و مسیر پشتیبان در گزارش تحویل ثبت خواهد شد. خواندن journal با حساب SSH فعلی مجاز نیست؛ نباید بدون دسترسی معتبر، سلامت لاگ برنامه ادعا شود یا مجوزهای سرور برای این قابلیت تغییر کنند.
